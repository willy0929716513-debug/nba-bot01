# nba-bot01

NBA 賠率分析機器人：抓取即時賠率與球隊戰績，套用蒙地卡羅模擬與 Kelly 準則計算推薦注碼，每日透過 Discord Webhook 推播；並附一個讀取同一份資料的靜態網頁儀表板。

## 功能

- **例行賽推薦（讓分）**：結合模型預測與市場共識線（`nba_bot.py`），每場比賽都會列出目前最佳盤口，並用蒙地卡羅模擬估計覆蓋機率、Kelly 準則建議注碼；Edge ≥ 8% 才算正式推薦（💎頂級／🔥強力／⭐穩定），未達標的場次會標示為「👀 觀察中」，兩者在網頁與 Discord 都看得到，但歷史記錄只會寫入 💎頂級（Edge > 12%）的推薦。門檻從原本的 6% 調高到 8%：小樣本（目前累積不到 50 場已結算）還不足以安全地重新校準機率模型本身，所以沒有去動機率/權重計算，而是提高「算不算正式推薦」的門檻——要求更大的 Edge 才出手，是降低雜訊、提高篩選嚴謹度的做法，不是宣稱模型變準了
- **大小分推薦（Over/Under）**：用同一套進攻/防守評分預測單場總分，跟市場大小分盤口比對、找出有 Edge 的一邊，算法跟讓分推薦完全對稱（含 Edge 門檻、分級、Kelly 建議、機率計算時都會把模型預測跟市場共識盤口混合，不是只看模型自己的數字），每場比賽的讓分跟大小分可以同時各自出現推薦，兩者各自獨立寫入 Gist 歷史記錄、分開自動核對、分開計算績效。2026-11-10 之前的大小分機率曾經完全沒混進市場共識（純模型自己的數字），已修復；網頁歷史紀錄頁另外有一張「大小分（修復後）」卡片，只統計修復後下的注，避免舊 bug 時期的紀錄混進去，看不出修復到底有沒有用
- **進階數據（四因子）**：從 ESPN 公開 JSON API（免費、不用金鑰）抓每隊球季至今的真實出手數據，算出 eFG%（真實命中率）、失誤率、進攻籃板率、罰球率、節奏（Pace，每場預估回合數），戰力排行頁可以看到每隊這幾項數字。節奏已經實際用來微調大小分的預測總分——兩隊都打得比聯盟平均快，預測總分會跟著調高，反之調低，這是之前完全沒有的考量；eFG%/失誤率/進攻籃板率/罰球率目前只做顯示用，沒有混進讓分的進攻/防守評分計算，避免跟既有以實際得失分為基礎的評分重複或衝突。這幾個數字沒有針對本專案自己的少量已結算注單去調整過，是套用標準公式在真實球季數據上算出來的
- **機率校準追蹤**：讓分跟大小分分開計算 Brier Score、Log Loss、預測分差/總分的平均絕對誤差（MAE）跟**帶正負號的平均偏差**（例如分差偏差 +6.3 代表模型預測的分差平均比實際高 6.3 分，不是隨機誤差，而是有方向性的系統偏誤），以及依預測機率分桶的校準表（例如模型說「70% 機率」的那組球賽，實際命中率是否真的接近 70%）。這是純粹的量測與記錄，**不是**擬合過的校準模型（Platt Scaling/Isotonic Regression）——目前累積的已結算樣本數太少（數十場），擬合校準器只會是在過擬合雜訊，所以刻意不做，只先把量測基礎建設做好，等樣本數夠大再考慮
- **週報/月報**：每逢週一自動附上近 7 天、每月 1 號自動附上近 30 天的績效與校準摘要（讓分/大小分分開），直接重用每日就在跑的排程，不需要額外的觸發設定
- **模型 vs 市場、第二套戰力評分（Elo）**：額外顯示 moneyline 盤口去抽水後的市場隱含勝率，跟模型自己的勝率並列比較；戰力排行頁也並列顯示一套獨立計算的 Elo 評分（標準公式）。兩者都只做顯示用，不會影響任何推薦或 Kelly 計算——樣本數還不夠驗證混進去是否真的有幫助
- **球隊戰力評分**：用 SRS（Simple Rating System）把每隊的場均淨勝分依對手強弱做迭代校正，不再只看勝率；另外比較每隊近期與整季的淨勝分算出「手感」，並比對賽程算出背靠背（0 天休息）的疲勞扣分，主場/客場扣分幅度不同
- **主場優勢採實際數據**：不再是全聯盟套同一個固定值，而是從本季真實比分算出聯盟平均主場優勢，再依各隊主場戰績往上/下微調（場次太少時會往聯盟平均收斂，避免早期幾場爆冷就讓數字失真）
- **串關推薦**：選腿依據不是推薦等級（💎頂級只代表 Edge 大，不代表模型講的勝率可信），而是讓分機率校準表上「跟這一腿同機率區間的歷史紀錄，實際命中率是否真的落在 65-70% 之間，而且要有 ≥10 場已結算樣本才算數」——用真實結算過的命中率去驗證，不是看模型自己講的數字。目前真實資料顯示沒有任何機率區間同時滿足這兩個條件（有的區間命中率不在範圍內，有的區間樣本數不夠），所以近期串關會常常是「今天沒有串關推薦」，這是刻意的：寧可不湊兩腿出來，也不用沒驗證過的區間硬湊。最多 3 場組成串關，求穩不求大，並明確提示串關全部腿都要命中才算贏
- **今日賽程**：列出當天全部例行賽賽事（不限於有推薦的場次），比賽結束後自動帶入比分
- **傷兵調整**：即時爬取 RotoWire 傷兵報告，依球星/主力等級套用不同扣分
- **夏季聯賽觀察**（`analyze_summer_league`）：僅在 6-8 月（`SUMMER_LEAGUE_MONTHS`）執行，抓 ESPN 比分與 The Odds API 盤口，產出戰績排行與盤口觀察名單；因陣容多為菜鳥/雙向合約、樣本數小，僅供參考，不計入 Kelly 資金配置。其餘月份完全不會呼叫對應 API，網頁與 Discord 訊息也不會顯示這個區塊
- **自動核對戰績**：每次執行會用 [balldontlie](https://www.balldontlie.io/) 的完整賽季比分，自動把之前「待開獎」的例行賽推薦結算成獲勝/落敗/走盤，並記錄實際比分，不需要再手動去 Gist 修改
- **歷史績效追蹤**：正式執行（GitHub Actions 排程）時將 💎頂級 等級的例行賽推薦、以及 Edge ≥ 6% 的夏季聯賽推薦（無 Kelly 資金配置）分開寫入 GitHub Gist，各自累積勝率/損益統計
- **網頁儀表板**（`docs/index.html`）：純靜態頁面，讀取每次執行輸出的 `docs/data/latest.json`，顯示今日推薦、串關建議、今日賽程、歷史績效與夏季聯賽分析（夏聯分頁僅在開打期間顯示）；透過 GitHub Pages 直接服務 `/docs` 資料夾
- **即時比分（網頁）**：網頁最上方釘住一條即時比分列，不管切到哪個分頁、往下滑多遠都看得到，每 30 秒自動更新一次。這是純瀏覽器端的功能，跟後端機器人一天只跑一次完全無關——直接在瀏覽器裡打 ESPN 公開的免費即時比分 API（跟四因子數據同一個來源），不用等隔天排程。顯示當天**全部**例行賽賽事，不限於有推薦的場次；有「真正達標」（Edge ≥ 8% 的推薦，不是每場都有的「最佳盤口」）的場次會排在最前面並標示「★推薦」
- **手機推播（選用）**：網頁釘選的即時比分列只有「開著網頁」才看得到；這個另外用 [ntfy.sh](https://ntfy.sh)（免費、不用註冊）在有真正達標推薦的比賽**開賽**跟**打完**時推播通知，手機裝 ntfy App 訂閱同一個 topic 就能在鎖定畫面收到。由另一個獨立的 GitHub Actions（`live_score_alerts.yml`）每 10 分鐘檢查一次，只讀當天已經產生的 `docs/data/latest.json` 來判斷哪些比賽有推薦，不會另外重跑整套分析；同一場比賽的同一個事件（開賽/打完）只會推播一次，用另一個獨立的 Gist 記錄狀態，不會跟結算用的歷史 Gist 互相干擾。沒有設定 `NTFY_TOPIC` 這個 secret 就完全不會啟用。ntfy.sh 匿名免費額度有每日訊息上限，一般個人用量（一天幾場比賽、每場最多兩則推播）不會碰到

## 執行方式

由 `.github/workflows/nba_odds_bot.yml` 排程觸發（每日台灣時間晚上 20:30，即 UTC 12:30），也可用 workflow_dispatch 手動測試執行（測試執行不會寫入歷史紀錄，也會標示為「測試版本」）。

## 所需環境變數 / Secrets

| 變數 | 用途 |
|---|---|
| `ODDS_API_KEY` | [The Odds API](https://the-odds-api.com/) 金鑰，抓例行賽與夏季聯賽盤口 |
| `DISCORD_WEBHOOK` | 推播結果用的 Discord Webhook URL |
| `GH_TOKEN` | 具 gist 權限的 GitHub token，讀寫歷史績效 Gist |
| `BALLDONTLIE_KEY` | [balldontlie](https://www.balldontlie.io/) API 金鑰，抓整季賽程與比分，用於動態調整球隊評分、自動核對戰績、產生今日賽程（未設定時戰績評分改用 `FALLBACK_RATINGS` 靜態評分，賽程與自動核對戰績功能也無法運作） |
| `NTFY_TOPIC` | 選用，設定了才會啟用「手機推播」功能（見下方）。topic 名稱本身要當密碼看待——[ntfy.sh](https://ntfy.sh) 沒有帳號機制，知道 topic 名稱的人都能訂閱或發送，所以挑一個夠長、不好猜的字串（例如一串隨機英數字），不要用 `nba-bot` 這種好猜的名字 |

## 網頁版

啟用 GitHub Pages（Settings → Pages → Source: Deploy from a branch，選這個分支、資料夾選 `/docs`）後，網址為：

`https://<你的 GitHub 帳號>.github.io/nba-bot01/`

每次 GitHub Actions 執行完都會自動把最新的 `docs/data/latest.json` commit 回分支，網頁會同步更新。

## 手機推播設定（選用）

1. 想一個夠長、不好猜的 topic 名稱（例如用密碼產生器產生一串隨機英數字），把它當密碼保管——不要貼在 issue、commit 訊息或任何公開的地方，這個 repo 是公開的
2. 到這個 repo 的 Settings → Secrets and variables → Actions，新增一個 secret：名稱 `NTFY_TOPIC`，值就是上一步想的字串
3. 手機安裝 [ntfy](https://ntfy.sh/) App（iOS/Android 都有，免費），開啟後訂閱同一個 topic 名稱
4. 測試是否設定成功：到 repo 的 **Actions** 分頁 → 選 `Live Score Alerts` → 右上角 **Run workflow** → 把「只發一則測試推播」的勾選框打勾 → Run。幾秒內手機就應該會收到一則測試通知；收不到的話先看那次執行的 log，如果寫「NTFY_TOPIC not set」代表 secret 沒設定成功（檢查名稱有沒有打錯），如果 log 顯示「ntfy push sent」但手機沒收到，大概是第 3 步訂閱的 topic 名稱跟 secret 裡的不一樣
5. 測試過關後，之後就讓它照每 10 分鐘的排程自動跑（不勾測試框的那個版本）——有真正達標推薦的比賽開賽或打完時，手機就會收到通知，鎖定畫面也看得到

不設定 `NTFY_TOPIC` 完全不影響其他功能，`live_score_alerts.yml` 每次執行只會記錄一行「沒設定，跳過推播」的 log，不會出錯。

## 已知限制

以下項目目前**沒有資料來源**，刻意不做、不假裝做到、也不捏造資料頂替：

- **進階數據（ORtg/DRtg）中的 DRtg**：balldontlie 免費版沒有 box score，但 ESPN 公開 JSON API（免費、不用金鑰，跟夏季聯賽比分同一個來源）有球隊級出手數據，已經可以算出 eFG%/失誤率/進攻籃板率/罰球率/節奏（Pace）跟**攻擊**端的 ORtg（詳見下方「進階數據（四因子）」）。但 DRtg 需要「對手打這隊時的真實節奏」，這個來源只給得出球隊自己的節奏，沒有對手配對過的資料，所以防守端的 ORtg（也就是 DRtg）目前還是沒做，刻意不拿自己的進攻節奏去湊一個假的防守節奏頂替
- **台灣運彩實際盤口**：The Odds API 是歐美盤口（DraftKings/FanDuel/BetMGM 等），不是台灣運彩，目前沒有串接台灣運彩的管道
- **多球季歷史資料集、真正的多季 walk-forward 回測、用 XGBoost/Logistic Regression 訓練模型**：沒有過去球季的完整歷史資料（盤口+傷兵+結果）可用，目前累積的真實已結算紀錄只有數十場，遠不足以訓練機器學習模型或做有統計意義的回測
- **Platt Scaling / Isotonic Regression 機率校準**：原因同上，樣本數太小，擬合校準器只會是過擬合雜訊
- **確定的賽前先發名單**：NBA 規則先發名單只在賽前 10-30 分鐘才正式公布，機器人一天只執行一次（跑的時候離當天賽事還有數小時），架構上就無法取得「確定」的先發名單，只能靠傷兵報告做近似
- **「穩贏」／保證獲利的邏輯**：這不是資料不足的問題，是運彩的本質——對一個有效率的市場而言，每一注都只有機率、沒有必然，任何宣稱「穩贏」的系統要嘛是在賭盤口效率不夠（罕見且不持久）、要嘛就是在自欺。目前讓分推薦在真實已結算紀錄上有穩定、合理的正期望值（勝率約 55%，高於打平所需的門檻），這已經是長期經營這類策略能合理期待的樣子，而不是「還不夠好，調一調就能變成穩贏」
